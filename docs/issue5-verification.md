## 未接続の依存と接続箇所

ユーザー確認済み：#7 のサービスマスターと #12 の「揉めるプラン」は未納品。データを推測で作らず、未接続を明示したPRとして進める。

- **#7 サービスマスター**：BoardClient の `services`（BoardService[]）へマスターの serviceId・表示名・kind を渡す。現状は空配列で、サービス新規追加ボタンを無効化。家族の付き添いの追加と既存サービス配置の移動・時間変更・削除は可能。
- **#12 デモ配置**：BoardClient の `demoPlacements`（Placement[]）へ正式 fixture の配置を渡す。現状は null で読み込み不可と表示。isDemo はルーム文書から取得し、URLやルーム名で判定しない。読み込みはPC幅のfamilyによる明示操作で commitRoomChange に保存する。
- **#9 検証エンジン**：lib/board-validation.ts の `validateRoomForBoard` を実エンジンへの委譲に差し替える。useRoomValidation は RoomSnapshot 全体を渡し、結果と入力 revision を組にする。現在の仮実装は ok=false・数字null・未判定理由を返すだけ。
- **#8 制約の承認画面**：既存の入力画面は雛形。週間ボード側には入力画面へのリンクと保存済み制約→careWindows確認→初期配置→ボード編集の順路を用意したが、制約の承認・保存そのものの通し確認は入力画面の実装後。
- **#6 警告表示**：BoardValidationStatus は revision 付き結果を受ける最小の受け渡し先。負担の集計・偏り・単位数・費用の計算は追加していない。

## 実環境での残りの確認手順

1. Firebase設定とデプロイ済みFirestoreルールを用意し、family参加済みルームの入力画面で制約とcareWindowsを保存する。
2. 週間ボードで順路を進み、付き添いを追加する。実Firestoreの placements と revision の増加を確認する。
3. ブロックをドラッグして曜日・開始時刻を変え、ブラウザをリロードする。
4. 順路を進んで変更後の配置が残り、現在の入力版で再検証されることを確認する。
5. 正式マスターとデモ fixture の納品後、サービス選択による新規追加とデモプランの明示読み込みを通し確認する。
