# デモ用 fixture（Issue 10・下書き）の説明

このドキュメントは `data/demo-fixture.json`（読み込みは `lib/demo-fixture.ts`）の
設計と検証の記録です。**これは担当（平林）のレビューで自分の物にしてもらうための
下書き**です。家族設定・文章・配置・期待値はすべてこのプロジェクト用に新規に
作成した架空の内容で、実在の人物・医療機関の情報は含みません。

## 構成

| 部分 | 内容 |
|---|---|
| `familyProfile` | 佐藤家の設定説明（fixture 専用メタ情報。Person 型の外） |
| `people` | 父（要介護3・被介護者、canProvideCare=false）、母・長女・長男（true） |
| `constraints` | 長女の仕事（平日9〜18時）、長男の平日不可、母の夜間不可、母と父の希望 |
| `hopes` / `unknowns` | 希望4件。unknowns は空（理由は後述） |
| `careWindows` | 平日＝朝7〜9時・昼12〜14時・夕17〜21時、週末＝午前8〜12時・夕17〜21時 |
| `copayRate` | 1（1割） |
| `documents` | 退院サマリー風テキストと家族メモ（Gemini 構造化の入力サンプル用） |
| `troubledPlan` | 「揉めるプラン」の配置24件と期待する検証結果 |
| `acceptedPlan` | 「納得プラン」の配置24件と期待する検証結果 |
| `fixedProposal` | 揉める→納得へ変換する固定 changes（正規化済み12件）と要約文 |
| `masterVersion` | 期待値の算出に使った単位数マスターの版（下記） |

配置 ID はデモモードの代替案と対応づけるため、すべて固定文字列
（`demo-` プレフィックス）です。

## 揉めるプランの再現ポイント（デモ台本との対応）

台本「3. ボードで揉める」で必要な3要素をすべて含みます。

1. **枠オーバー**：週合計 6,564単位 → 月換算 28,131単位（上限 27,048 を 1,083単位超過）。
   自己負担は月 37,878円（枠内分 27,048円＋超過分全額 10,830円）。
   内訳は訪問介護（身体介護）2時間×週3回、通所介護（月・金7時間／水3時間）、
   通所リハビリ7時間×週2回。
2. **空白**：水曜の昼 12:00〜14:00。水曜の通所介護が午前（9〜12時）で終わり、
   昼の careWindow を誰も埋めていないことで生じます。この1件だけに絞ってあります。
3. **負担集中**：長女の付き添いが週27時間（出勤前の見守り週4時間＋平日夜の
   入浴介助・就寝準備15時間＋週末8時間）で過労ライン（週20時間超）に当たります。
   母は週10時間、長男は週8時間です。

なお、揉めるプランに hardViolations（対応不可時間への配置など）と
validationErrors は含めていません。警告の種類を台本の3つに絞るためです
（長女の平日夜の配置は仕事の終了時刻18時に合わせ、違反にならない形にしています）。

## 納得プランと固定 changes

`fixedProposal.changes`（resize 8件・remove 2件・add 2件の計12件）を
揉めるプランへ適用した結果が `acceptedPlan` です。検証結果は **ok=true**：
週 5,622単位 → 月換算 24,094単位（枠内）、自己負担は月 24,094円、
空白なし、負担は母12時間・長女18時間・長男12時間に分散します。

変更の物語上の意味：
- 水曜の通所介護を終日（9〜16時）に延ばす → 昼の空白が消える
- 火・木の通所リハビリを 10〜14時に短縮 → 単位数を削る
- 金曜朝の訪問介護を母の見守りに替える → 単位数と費用を削る
- 平日夜を母（17〜19時）と長女（19〜21時）で分ける → 長女の連続負担を減らす
- 土曜午前を長男に替える → 長女の負担を分散する

## 期待値（expectedValidationResult）の算出方法

**実エンジンで算出しました**（推測や手作業の埋め込みではありません）。

- Issue 5/6 の下書き作業ツリーにある単位数マスター（`data/units.json`、
  `masterVersion: reiwa6-basic-units-v1` ＝ 令和6年度介護報酬の基本単位）と
  検証エンジン `validateRoom` に、fixture の people／constraints／careWindows／
  copayRate／各プランの placements を入力して得た出力をそのまま格納しています
- 固定 changes についても、同ツリーの `applyChanges` で適用結果が
  `acceptedPlan.placements` と完全一致することを確認しています
- 確認は一時テストで実施し、3件（両プランの検証結果一致・納得プラン ok=true・
  changes 適用一致）すべて通過を確認後に一時テストは削除しました

**再計算が必要になる条件**：単位数マスター（units.json）の数値が Issue 5 の
確定で変わった場合、その版に合わせて両プランの期待値を再算出してください
（`masterVersion` を新しい版に更新すること）。配置・制約・careWindows を
変えた場合も同様です。計算エンジン（Issue 6）は main に統合済みで、
両プランの期待値は実エンジン（validateRoom）の算出結果と一致を
確認済みです（平林の独立計算でも全項目一致。docs/fixture-check-hirabayashi.md）。

## unknowns が空の理由

fixture は「入力画面で家族が構造化結果を確認し、制約を確定した直後の状態」を
表します。プランの確定は unknowns が空であることが条件（Issue 14）のため、
デモが確定まで一本で通るよう空にしています。家族メモと退院サマリーのうち、家族の都合と希望は
constraints／hopes に反映済みの形で書いてあります。父の介助ニーズ
（入浴の介助・服薬の確認・通所リハビリの継続など）は constraints／hopes
ではなく、プランの配置（placements）の側で表しています。実AIの構造化直後の下書きで unknowns が
出るのは通常の流れで、それは Issue 7 の確認画面で解消してから保存します。

## baseRevision について

`fixedProposal` は Proposal 型から `baseRevision` を除いた形で保持しています。
baseRevision は実行時に取得したスナップショットの revision を使うもので
（共通前提の正規化契約）、fixture には固定しません。Issue 15 がデモ固定案を
発行する時点で付けます。

## 平林へのレビュー観点（例）

- 家族設定と書類の文章が、自分の想定するデモの語りと合っているか
- 揉めるプランの「置き方」が、家族がとりあえず組んだプランとして自然か
- 納得プランの変更が、ピッチで説明しやすい流れになっているか
- careWindows の時間帯（特に昼12〜14時）が想定と合っているか
